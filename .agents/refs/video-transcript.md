## TL;DR — the system in three phases

1. **Ideation / strategic planning** (project level): brain-dump → have the agent ask
   clarifying questions one at a time → `/create-prd` (conversation → structured PRD) →
   **human reviews the PRD** → `/create-stories` (PRD → stories markdown + optionally
   create GitHub/Jira issues, asks before creating).
2. **PIV loop** (per ticket): `/prime` (load codebase + the issue as context, read recent
   git commits as long-term memory) → free-form exploration (often with sub-agents for
   research to protect the main context window) → `/plan` (conversation → structured
   `*.plan.md` with patterns, files to change, task order, self-validation strategy) →
   **start a FRESH session** → `/implement <plan>` (delegate coding + self-validation:
   tests, lint, type-check, optional e2e via agent-browser) → human code review + manual test.
3. **System evolution** (the most powerful part): when the agent does something wrong,
   don't just patch the bug — fix the AI layer that allowed it. Update global rules
   (`CLAUDE.md`), commands, skills, on-demand context, and plan/PRD templates. Check these
   into source control and PR-review them like code, so the whole team benefits.

Key principles:
- Not vibe coding — the human stays in the driver's seat via planning + validation.
- Keep it simple on purpose; mold these foundations to your SDLC rather than adopting a
  bloated off-the-shelf framework (BMAD, GSD, Spec-kit, etc.).
- Anything you prompt more than ~3 times → turn into a command or skill.
- Two planning layers: layer 1 (PM-level, high level, no code) vs layer 2 (task-level, in
  the weeds of the codebase).
- Separate PRD and stories steps so you can review the PRD before generating stories.
- Separate planning and implementation sessions to keep the agent focused and unbiased.
- Use git history as the agent's long-term memory.
- Use sub-agents for research so the main agent isn't overwhelmed (a million-token window
  doesn't mean you should fill it).
- Every artifact (PRD, stories, plan, code) gets human-in-the-loop review.

We cut a fresh session, sent the plan into implementation, and then we'll wait for it to write the code, do all of its own validation, and then we'll also step in and do a code review. It's not like you have to do this — some people are a big fan of just shipping the code right to production and having the coding agent do its own work. ### Phase 3: System Evolution

The last thing I want to talk about is system evolution. Whenever we do a PIV loop, it is very far from guaranteed that the implementation will be perfect. Coding agents are not perfect — they are non-deterministic by nature. Even if we work super hard to align with it in the planning phases, there are still going to be mistakes. But the powerful part of this system is we don't have to just treat the bug as a one-off fix that we address and then move on. We can spend some time to also fix the system that allowed the bug. We can have a retroactive session with the coding agent where we say: okay Claude, you allowed this problem to creep into my codebase. I want you to dive into your AI layer — take a look at your rules, your commands and skills, the process, the workflow I brought you through. I want you to identify things that we could improve so that this kind of issue doesn't happen again. For example, maybe the new feature looks really ugly because it didn't create the component in the same style as the rest of our codebase. Maybe that means there's something in our global rules we have to update for our style conventions. Or maybe we need to build something into our validate workflow where whenever we validate the codebase, we make sure that any new front-end component is in compliance with the styles of our other components. The point is: generally when your coding agent does something wrong, there's going to be something in the context you give it that you can improve — using it as an opportunity to continue to evolve your AI layer, making your rules more specific over time, making your workflows more reliable.

The best part is when you use every single Jira ticket as potentially an opportunity to improve your system, you get to improve the whole process for everybody — because you can check in your rules and commands and skills into source control just like your codebase. The entire team can reuse these things, and you can even create pull requests to update commands just like you create pull requests to update your codebase, so you can do code reviews making sure everyone's in line with the changes. It's high leverage because every single time you improve a command or a skill, it might save engineers dozens of hours going forward. The four things I generally improve over time in a codebase: my commands, my on-demand context (this could even mean things in Confluence — optimize your documents for AI understanding), my global rules, and my plan and PRD templates (find and fix gaps over time). For every codebase, I'm constantly doing this: if I have a PIV loop where there is some major issue, I step outside the PIV loop to do this system evolution, update things I created up front, and then go into the next PIV loop. If there are no issues at all and the coding agent completely rocked that Jira ticket, then you just loop right back — go through the planning process, load that next Jira ticket. It becomes very cyclical. There are basically two loops: the inner loop when everything's working well and you're chugging through the work, and the outer loop when you're taking some time to reflect and make your system better. It's not like you always have to do the outer loop, but I encourage you to do it pretty often because not only are you improving your commands, you are also customizing your process to your specific codebase over time. All of the commands and skills I have are a starting point, but they're more general — if you want to really optimize something for your process, start with these and find opportunities to make them more specific to your validation strategy or planning strategy.
